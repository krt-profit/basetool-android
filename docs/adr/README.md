# Architecture Decision Records

Every architecturally significant decision for the Android app is recorded here **before or
with** the change that implements it (same discipline as the main `basetool` repo).

Format: `NNNN-short-kebab-title.md` with sections *Status* (proposed / accepted / superseded
by NNNN), *Context*, *Decision*, *Consequences*. Numbering starts at 0001 and is
repo-local — main-repo ADRs (e.g. the API-exposure and mobile-auth ADRs from Phase 0) are
referenced by their repo-qualified id, never renumbered here.

| ADR | Decision | Status |
|---|---|---|
| [0001](0001-core-module-split-and-network-layer.md) | `core:common` (logging facade) and `core:network` (client, mandatory headers, problem→state mapping) as separate modules; `core:auth` will depend on `core:network` and implement its `AccessTokenProvider`, which is **synchronous** because it is read from an OkHttp interceptor. Errors are classified by the backend's stable `code`, not the HTTP status — 403 covers pending approval, the terms gate and a real authorisation failure, and a status-based client shows the wrong screen for two of three. No HTTP disk cache (it would be a second copy of member data outside every wipe path) and a `Date`-header-derived `ServerClock` for DPoP proof timing (Keycloak allows 10 s lifetime / 15 s skew, tighter than mobile clock drift). Hilt modules deliberately follow with `core:auth`. | Proposed |

| [0002](0002-refresh-token-at-rest.md) | The refresh token is kept AES-256-GCM encrypted under a non-exportable Keystore key bound to an unlocked device, ciphertext in a Preferences DataStore, excluded from backup in both rule sets. The decision that shapes the code is the **`SecretCipher` seam**: the Keystore cannot run on a JVM, so the cipher is the fake and everything above it — what is written, what happens when it cannot be read, what a wipe removes — is tested for real. An unreadable token is a state (`null` + clear), not an exception, because the three ways it happens all mean "log in again" and throwing would crash on start-up. The backup exclusion is pinned by a test reading the XML against a published path constant: it is the one failure here with no symptom, and the placeholder rules this change inherited would have matched nothing. Open and marked so: the Keystore implementation and the restored-backup check both need a device. Rejected: security-crypto (deprecated, no successor), persisting the access token, a credential-derived key, Robolectric shadows instead of the seam. | Proposed |

| [0003](0003-token-endpoint-client.md) | Token traffic runs on its own `OkHttpClient`, derived from the API client but stripped of its interceptors: `MandatoryHeadersInterceptor` would put an `Authorization` header on Keycloak's token endpoint, which answers `invalid_client` — an app that logs in once and can never refresh. `ServerTimeInterceptor` is re-added alone, because this is the only traffic that observes the clock a DPoP proof is judged against. Endpoints are derived from the issuer rather than discovered, which also makes the `/userinfo` ban structural (Keycloak answers 500 there under the refresh-only policy). Outcomes are states: `invalid_grant` and a misconfigured realm both arrive as HTTP 400 and only the first means "log in again", and a 2xx with `token_type` other than `Bearer` is named rather than handed on — its symptom is a 401 storm that accuses the backend. The RFC 9449 nonce retry is implemented although the realm demands no nonce, so enabling one is not a client-breaking change. Rejected: one client with per-request overrides, AppAuth (no DPoP), throwing on refusal, startup discovery. | Proposed |

| [0004](0004-session-model.md) | The session keeps **`Stale`** apart from **`SignedOut`**: only `invalid_grant` clears a stored token, so a tunnel does not become a logout and the member is not asked for a password they never needed. Refreshing is single-flight (mutex + re-check) — several screens loading at once would otherwise each start one, each with a DPoP proof to verify and all but one result discarded; the test asserting it was verified to fail with the lock removed. A refresh response without a `refresh_token` keeps the stored one, because the realm does not rotate and `null` would discard the only way back in. The three per-attempt login secrets (PKCE verifier, `state`, `nonce`) live in one object; `state` is checked before anything else in a redirect is read and the `nonce` is verified against the ID token, or it is decoration. Redirects are parsed at string level — the dev realm's custom scheme is not a URL any HTTP parser will touch. The ID token's signature is deliberately not verified (OIDC Core 3.1.3.7: direct from the token endpoint over TLS), and `deleteKey()` became part of the `SecretCipher` contract because a cipher that cannot be wiped cannot back a logout. Rejected: one failure state for every refresh error, refreshing inside the interceptor, JWKS validation, skipping the nonce. | Proposed |

| [0005](0005-browser-round-trip.md) | The in-flight login attempt is **persisted, encrypted and single-use**: the Custom Tab belongs to another app and the system may kill this process behind it, so `state`, `nonce` and the PKCE verifier live in the same encrypted store as the refresh token — a ViewModel field works on a developer's device and fails on a member's, once, unreproducibly. A dedicated `singleTask` `AuthRedirectActivity` catches the redirect rather than `MainActivity`, which sits *below* the browser and would be created a second time on top of it; giving `MainActivity` `singleTask` would impose one flow's need on every deep link in the app. The redirect URI is per flavour — verified App Link in production, custom scheme on the dev realm only — and the post-logout return is claimed too, or the browser leaves the member on the website after a logout. Endpoints come from `BuildConfig` alone: no runtime switch, no debug menu. Rejected: the attempt in memory or in plain preferences, the filter on `MainActivity`, a production custom scheme, `WebView`. | Proposed |
| [0006](0006-minsdk-30.md) | **minSdk rises to 30 and the API-29 app-lock path is deleted rather than fixed.** API 29's only auth-bound key is time-bound, which no `CryptoObject` accepts and whose `Cipher.init` throws until an authentication exists — the opposite order from API 30+. Both preparation calls ran before the prompt, so on the whole minSdk platform the lock could neither be armed nor opened, and a broad catch reported it as permanently unsatisfiable; unit tests and every API 37 run stayed green. One key kind now, every prompt bound to its operation, and `AppLockKeystoreContractTest` exercises the contract against a real Keystore on a device. Rejected: keeping 29 with the fix (a second path only the floor exercises), keeping 29 without the lock (a security feature silently absent reads as a bug). | Accepted |

| [0007](0007-per-app-language-via-appcompat.md) | **The in-app language is the platform's per-app language; the app keeps no copy.** `AppCompatDelegate.setApplicationLocales` is `LocaleManager` on API 33+ and AppCompat's backport below, so the choice and Android's own "App languages" screen are one value rather than two that disagree without an error. The cost is explicit: `MainActivity` becomes an `AppCompatActivity` (the backport applies only to AppCompat delegates below API 33), `Theme.Basetool` reparents to `Theme.AppCompat.NoActionBar` or the activity refuses to start, and the manifest opts into `autoStoreLocales` so the choice survives a cold start on API 30–32. The control highlights the language *on screen* rather than the stored tag, which are different facts until the first tap. Rejected: a DataStore preference of our own, a hand-rolled `attachBaseContext` wrapper, raising minSdk to 33. | Accepted |

| [0008](0008-generated-wire-models.md) | **Wire models are generated from the backend's committed `openapi.json`; API interfaces are not.** A generated client would have to be unwound at every call site — the repositories classify failures by the backend's problem `code` rather than by HTTP status, fold some refusals into successes, and page-walk catalogs — so the generation is taken for the payload types and stops there, and Retrofit is not adopted. Three things had to be solved before the models were safe to decode rather than merely to compile: decimals (`@Contextual` does not reach a type argument, so `Map<String, BigDecimal>` does not compile — `KrtDecimal` carries its own serializer and keeps every digit), strict enums (kotlinx throws on an unknown constant, which the server is free to add and which is read on the login path — `coerceInputValues` turns it into `null`), and Spring's untyped `ProblemDetail`, which is refused by a generator-ignore file because `:core:network` has the typed one. Rejected: Retrofit + generated interfaces, `Double` for money, a hand-maintained model allow-list. | Accepted |
| [0009](0009-tablet-settings-ships-without-its-befoerderung-column.md) | **The tablet's Einstellungen ships with only the left of design ch. 13's two columns.** The right column is Beförderung, whose screen is built and tested but withheld by the owner (#66) because the handoff has no chapter for it, so its destination renders a placeholder — and pairing the settings with a placeholder on every tablet is worse than the honest half. Recorded rather than left implicit because the previous in-code justification for the same gap had gone stale unnoticed: it blamed a backend read that had since shipped. Expires with #66; every other tablet layout in the handoff was built in the same pass. | Accepted |
| [0011](0011-the-app-knows-its-permissions-and-refuses-in-place.md) | **The app reads its permissions, and a gated control refuses in place instead of hiding.** `Identity` kept a user id and two booleans because holding more "would put personal data in memory" — but `/api/v1/users/me` returns `roles` and `permissions` in a response the app already parses, and the access token carries the realm roles anyway. The roles were in the process either way; dropping them only meant not being able to read them. Three of twelve ViewModels fetched the identity at all and the Lager fetched none, so a plain `KRT Member` was offered Zuordnen, Buchen and Umbuchen on org stock and refused three times. Gated controls now render at the ladder's disabled alpha, stay **tappable** — `enabled = false` receives no tap and a control that cannot be tapped cannot explain itself — and name the missing grant rather than the status code. Not hidden, because this org grants roles by hand and an invisible feature is one nobody asks for. Rejected: hiding them; letting 403 do the talking; deriving authorization from the token's Keycloak roles, which would put a second, drifting copy of the role matrix in the client. | Accepted |
| [0010](0010-screenshot-protection-is-member-switchable.md) | **`FLAG_SECURE` becomes member-switchable, fail-closed.** It was unconditional, which also blocked the one capture the project wants: a tester's screenshot of a defect, and crash reporting here is local-only, so a picture is often the whole report. `MainActivity` sets the flag before `setContent` and clears it only after the stored preference has been read, so an unset key, a slow read and a failed read all mean blocked. The switch sits under "App" in Einstellungen, phrased as "Screenshots erlauben" rather than as lifting a protection, and lives in its own store so a logout does not silently restore the block. Rejected: dev-flavour-only (testers install the prod APK), unauthenticated screens only (the bug worth photographing is behind the login), a hidden gesture. | Accepted |
| [0012](0012-sign-out-asks-before-it-wipes.md) | **Sign-out in Einstellungen asks before it wipes; the gates' sign-out does not.** Design ch. 13 draws the button without a confirmation and pairs its only danger modal with "Lokale Daten löschen", a control that has not shipped — so the artboard is silent on this question rather than opinionated about it. What it could not weigh is the cost: `REQ-APP-AUTH-005` deletes the encrypted refresh token, the non-exportable Keystore key and the DPoP signing key, nothing on the device restores them, and the way back is the full browser round trip. That sits at the foot of a scrolling list of toggles that are all undone by a second tap. The button keeps its rung, label and placement and gains a danger-tone `KrtModal` whose body names the consequence; the confirm action reads "Jetzt abmelden" so it cannot be confused with the screen's own button. The gates' sign-out (approval-pending, gate-unavailable, locked) stays direct: there it is the only way forward, not a mis-tap risk. Rejected: leaving it as drawn, moving it into an overflow, a toast with an undo (there is nothing to undo). | Accepted |
| [0013](0013-the-lock-screen-has-one-button-because-the-prompt-has-two.md) | **The lock screen keeps one unlock button, not the artboard’s two.** Chapter 04’s artboard 5 draws „MIT BIOMETRIE ENTSPERREN“ plus a quieter „GERÄTESPERRE VERWENDEN“ underneath, and its own annotation says both open the same sheet. That sheet is `BiometricPrompt`, configured `BIOMETRIC_STRONG or DEVICE_CREDENTIAL`, which draws the PIN fallback inside itself as a control this app neither owns nor styles. A second button would open the sheet the first one opens and imply that the first had not — that biometrics were the whole offer and the PIN needed its own door. The label follows: „Mit Biometrie entsperren“ describes a button standing beside an alternative, and on a button that opens both paths it names one and hides the other, so the screen keeps „Entsperren“. Contingent on the authenticator set, not on taste: drop `DEVICE_CREDENTIAL` and both the second button and the artboard’s label become right again. Rejected: drawing both as designed; keeping one button with the artboard’s label; an in-app PIN pad, which would be a credential this process could read. | Accepted |
| [0014](0014-every-datastore-is-owned-by-the-application.md) | **Every DataStore is owned by `BasetoolApplication`, and a source-scanning test enforces it.** DataStore allows one active instance per file per process and throws fatally on the second — at the point of first *read*, never where the duplicate was made, so the app just vanishes to the home screen and reads as a crash in whichever screen was opening. It happened twice in the same shape: the token store, built once per *activity* while documenting itself as once per process, died on a language change; the settings store repeated it and died on the commonest path there is — tapping a notification, whose `PendingIntent` carries `FLAG_ACTIVITY_NEW_TASK`, which makes Navigation rebuild the task and finish the activity so the replacement opens a second `krt_settings`. The first fix was correct, well explained beside the code it fixed, and carried nothing forward into the build, which is exactly why a second store written in a different file could repeat it. So the rule now fails the build: `ProcessStoreOwnershipTest` reads the sources, names the offending file and says where the store belongs. Per-activity *effects* stay with the activity — the screen-capture window flag does — the store behind them does not. Rejected: another comment; a Hilt scope (the stores are not injected); a reflective check, which could only see the store it managed to reach. | Accepted |

| [0016](0016-the-app-renders-the-approval-the-api-has.md) | **The bank's request rows render the approval the API has, not the one the artboards draw.** Design chapter 12 shows an approval counter — „1 / 2 FREIGABEN", „BESTÄTIGEN ( 2/2 )", a ladder of two and three approvals — and `BankBookingRequestDto` carries no count at all: one owner approval, outstanding or given (`REQ-BANK-041`), with a bank employee's confirmation as the second step on a surface the app does not carry. The ladder is real but escalates *which class* must approve on the KRT account (`REQ-BANK-047`), never how many. So the app names the class it waits on, offers grant and revoke but no reject (the member has no reject endpoint), and drops the deposit's threshold hint entirely (`REQ-BANK-042` makes a deposit approval-free, which the web frontend states in its own copy). No backend change; the artboards go back for correction as round 7. Rejected: faking the fraction client-side, which would lie on the first KRT request; and adding a tally to a settled audited flow to satisfy a mockup. | Accepted | 2026-08-27 |
| [0017](0017-type-resolved-detekt-joins-check.md) | **`:app:check` now runs `detektMain`, the type-resolved detekt.** `check` gated only the plain `detekt` task, which analyses without type resolution, so the whole family of rules that needs it ran nowhere -- measured: an unused private function passes `:app:detekt` and fails `:app:detektMain`. Five unused private declarations had accumulated across four screens before anyone looked. Two build fixes had to land first: `BuildConfig` is generated Java and was unresolvable, costing 40 "compiler errors" a run that detekt reports only as a one-line accuracy caveat (the fix is `setFrom`, never `from` -- the plugin holds that classpath as a Gradle *convention*, and `from()` replaces a convention rather than adding to it: 92 entries collapsed to 1 and 40 errors became 14021); and the variant tasks take their source from the Android variant rather than the extension, so generated OpenAPI DTOs produced 406 unfixable findings, excluded now by a path spec because an ant pattern matches nothing against a flat file collection. Scoped to `:app`: `:core:auth` and `:core:network` are kotlinx.serialization code, detekt loads no Kotlin compiler plugins, and the resulting findings are partly false. Verified by making the gate fail, then removing the probe. Rejected: a baseline file, relaxing the three rules that fired, gating one variant. | Accepted | 2026-08-28 |
| [0018](0018-the-verwaltung-is-a-tab-and-briefing-is-renamed-out-of-a-collision.md) | **The Einsatz's Verwaltung is its eighth tab, drawn only for a manager — and the first tab is renamed „Briefing" out of a label collision.** Round 10 had asked the designer whether the undrawn Verwaltung half is one sheet from the head or per-tab affordances (§ 10a); pending an answer the app shipped a `KrtBottomSheet` behind a full-width ghost button wedged between the pinned head and the tab row. The owner rejected both halves on sight: the button was the shape this app falls back to whenever an artboard is missing, and the screen carried **two controls labelled „Übersicht"** — the shell's Home destination and the Einsatz's own first tab — about 200 dp apart, which cost a real mis-tap. So the Verwaltung becomes a tab (back means „leave the Einsatz", a section can be saved and re-read in place, and it matches the web's own `mission.tab.admin=Verwaltung`), **locked rather than hidden** for a caller the server's `canEdit` says may not manage — amended 2026-08-29: the first version hid it, and the design handoff's round-7 audit rejected that, because this organisation grants roles by hand and a function nobody sees is never requested. The first tab becomes „Briefing", which is both unambiguous and more accurate. Rejected: renaming the shell's destination („Übersicht" is fixed by ch. 03 and appears everywhere), and keeping web parity on the tab label (parity is the lowest of the three precedence levels). | Accepted | 2026-08-29 |
| [0019](0019-pinning-build-time-transitives.md) | **Nine vulnerable build-time transitives are pinned as dependency constraints from the root build script.** All nine were undeclared — BouncyCastle, jose4j, jdom2 and commons-lang3 through AGP 9.4.0, plexus-utils through licensee, handlebars through the OpenAPI generator, and bcprov 1.81 (the one **critical**) through Robolectric's unit-test classpath — so Dependabot could propose nothing and no plugin release moved them. `prodReleaseRuntimeClasspath` resolves none of them, but build-time is not the same as does-not-run: bcprov signs the release APK, commons-lang3 and httpclient run inside Lint, handlebars writes 819 source files. **Constraints, not `force`**, because a constraint only raises — so the pins can sit at advisory floors below the newest release and a future upstream shipping higher still wins; `force` would silently downgrade one that had legitimately reached the APK. In the root script, not `settings.gradle.kts`, where `VersionCatalogsExtension` does not exist yet and ten versions would have to be hardcoded outside the catalog. Measured no-op on what ships: byte-identical APK, byte-identical generated DTOs. Rejected: bumping the plugins (no release exists), `dependency-graph-exclude-configurations` (closes the alerts by hiding them, and degrades the release SBOM), dismissing all nine as build-time-only. | Accepted | 2026-09-04 |

| [0020](0020-one-codeql-query-is-filtered-out.md) | **`java/local-variable-is-never-read` is excluded from CodeQL; `java/field-masks-super-field` is fixed at source instead.** The first raised 30 alerts and all 30 named `tmp0_other_with_cast` — the Kotlin compiler's temporary in the `equals` it synthesises for a property-less `data object`, reported at line 1 column 1 because it has no source range. 31 of 31 findings this rule has ever produced here were compiler-generated, and no edit satisfies it short of abandoning `data object`. The second had a real fix: `LoginUiState` was the only `sealed class` against 46 sealed interfaces, and the Compose compiler's `$stable` marker on parent and members is genuine shadowing — so it became a sealed interface and the rule stays armed as the detector for the next one. **The exclusion costs real coverage and the ADR says so**: under K2 `allWarningsAsErrors` does *not* catch an unused local (it is an IDE inspection), and detekt's equivalent runs only in the type-resolving tasks ADR-0017 gates for `:app` alone — so `core:*` now has no gate at all. Weighed against 30 permanent findings plus one per new screen. Rejected: `security-extended` (a measured strict downgrade — drops 122 quality queries to silence one), per-alert dismissal (per-location, reopens on every new `data object`), rewriting 80 `data object` declarations, inline suppression (anchored at L1:C1, one comment per file forever). | Accepted | 2026-09-04 |


| [0021](0021-blueprint-sharing-belongs-to-the-account-not-the-app.md) | **„Blueprints mit Org teilen“ moves from APP to KONTO; artboard 13-2 is overruled.** The two documents governing the screen had disagreed since it was built: `REQ-APP-SET-010` is titled *„Three account rows, and the one version two of them share“* and says artboard 2 puts three things in KONTO, while artboard 2 draws only two there and puts blueprint sharing under APP beside „Sprache“. The implementation followed the artboard, which is the correct default — and nobody noticed the requirement said otherwise, because its sentence reads as a summary of the drawing rather than a rule. **APP holds what lives on the device and survives a logout; KONTO holds what lives on the account.** Blueprint sharing is written to the server, is visible to the organisation and follows the member to any device, so it was grouped by where the control is rather than by what it changes. The practical half: it shares one optimistic-lock version with the payout preference, the two fail together and their retry is one action — a relationship a section boundary made invisible. Filed as a deviation (round 17 § D1) so the design side can redraw or refuse. The requirement's sentence is dated rather than rewritten. | Accepted | 2026-09-05 |

# ADR-0006 — minSdk 30, and no second path for the app lock

- **Status:** Accepted
- **Date:** 2026-08-19
- **Deciders:** @greluc
- **Related:** ADR-0002, `REQ-APP-AUTH-010`

## Context

The app shipped with minSdk 29, chosen for reach: roughly 91 % of active devices at the time
(ANDROID_APP_PLAN, Statcounter 04/2026). The difference between 29 and 30 in that figure is
small; the difference in what the app had to *do* was not.

API 29 has no `setUserAuthenticationParameters`. Its only auth-bound key is the *time-bound*
kind produced by `setUserAuthenticationValidityDurationSeconds`, and Android refuses to pair
one with a `BiometricPrompt.CryptoObject`. So the app lock needed two paths that differ in
more than strength:

| | Key | `Cipher.init` before authentication |
| --- | --- | --- |
| API 30+ | auth-per-use | succeeds — bind it into the `CryptoObject` |
| API 29 | time-bound | **throws `UserNotAuthenticatedException`** |

They run in **opposite orders**. On API 30+ the cipher is created first and the prompt vouches
for it. On API 29 no cipher can exist until an authentication does, so it can only be built
afterwards.

That inversion produced a defect that shipped and stayed invisible: both preparation calls ran
before the prompt, so on API 29 both threw. Arming failed outright; unlocking was worse,
because a broad `catch (GeneralSecurityException)` turned the throw into `null` — already the
value meaning *this key is invalidated, the lock can never be opened again*. **On the entire
minSdk platform the lock could neither be armed nor opened, and the app reported it as
permanently unsatisfiable.** Every unit test was green, and so was every run on API 37; it
surfaced only when the Keystore contract was finally exercised on an API 29 device.

## Decision

**minSdk becomes 30, and the API-29 path is deleted rather than fixed.**

- `AppLockKey` creates exactly one kind of key, with
  `setUserAuthenticationParameters(0, BIOMETRIC_STRONG or DEVICE_CREDENTIAL)`.
- `AppLockKey.SUPPORTS_CRYPTO_OBJECT` and `LEGACY_VALIDITY_SECONDS` are gone.
- `BiometricGate.prompt` no longer takes `useCryptoObject`; every prompt is bound.
- `AppLockKeystoreContractTest` runs the contract against a **real Keystore** on a device, which
  is the only place either defect was ever visible.

## Consequences

**The weaker binding is gone.** Every authentication now vouches for the exact operation rather
than for a recent moment in time. That was the compromise API 29 forced, and it was documented
as looser-but-still-cryptographic; it no longer has to be argued at all.

**One less way for the lock to be wrong.** The class of bug here was not "API 29 is weaker" but
"two paths, one of them rarely run". A path exercised by neither unit tests nor the usual
emulator is a path that is wrong until proven otherwise — and this one was.

**Android 10 devices lose the app.** They keep the web app, which is the same product and the
reason the loss is acceptable. The Play listing simply stops offering an install below API 30.

**`compileSdk`/`targetSdk` are unchanged at 37.** This raises the floor, not the target.

## Alternatives considered

**Keep 29 and keep the fix.** The fix worked — verified on an API 29 device. Rejected because it
preserves a second path that only a device at exactly the floor exercises, and the cost of that
was already demonstrated once. A correctness argument that depends on somebody remembering to
test the oldest platform is not one worth carrying for a few percent of reach.

**Keep 29 and drop the app lock there.** A security feature that is silently absent on the
oldest devices is worse than an app that does not install: the member cannot tell, and the
setting's absence reads as a bug rather than as a decision.
